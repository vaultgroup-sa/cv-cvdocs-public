# Authorization

A few API endpoints allow anonymous access.
All the rest require authorization using `Bearer` token which is JWT:

`Authorization: Bearer <JWT>`

For details about authorized client types (`unit`, `user`, `supervisor`) and permissions see [security] document.

# Actuator

Every application (microservice) exposes two anonymous (no authorization required) actuator endpoints:

* `/actuator/health` – a simple health check endpoint;
* `/actuator/info` – exposes some information about application (like artifact, version and timestamp of build).

# General

All the date/time values across all API endpoints are represented in ISO-8601 timestamp format unless explicitly stated
otherwise.
The part which represents fractions of second is optional (both examples are valid):

* `2022-05-05T10:19:03.432Z`
* `2022-05-05T10:19:03Z`

In case of error a proper HTTP response code is used and the `application/json` response body format is as follows:

```json
[
  {
    "message": "Certain error occurred"
  },
  {
    "field": "unit_id",
    "message": "Invalid UUID value"
  },
  ...
]
```

There is an array of one or more error objects. Each one must have `message` property which contains human-readable
description of what went wrong.
If an error is related to a certain request param, path variable or form field then the error object will also
have `field` property.

There are plenty of validation errors caused by malformed or unexpected values of certain request parameters
or `application/json` request body object properties. So keep that in mind and make sure to provide generic error
handling.

# Audit endpoints

## POST `/audit/log`

Submit unit audit log(s) for processing/storing.

#### Access: `unit`, no permissions required

#### Request body: `application/json`

```json
[
  {
    "version":1,
    "code": 100,
    "app": "cv",
    "priority": "low",
    "capture_time": "2022-05-05T10:18:41Z",
    "description": "Test log #1",
    "level": "Debug"
  },
  {
    "version": 1,
    "code": 101,
    "app": "cv",
    "priority": "norm",
    "capture_time": "2022-05-05T10:18:53Z",
    "description": "Test log #2",
    "level": "Debug"
  },
  {
    "version": 1,
    "code": 102,
    "app": "cv",
    "priority": "med",
    "capture_time": "2022-05-05T10:19:03Z",
    "description": "Test log #3",
    "level": "Debug"
  },
  {
    "version": 1,
    "code": 103,
    "app": "cv",
    "priority": "high",
    "capture_time": "2022-05-05T10:19:19Z",
    "description": "Test log #4",
    "level": "Debug",
    "parameters": [123, true, {"foo": "bar"}]
  }
]
```

*Required fields:*

* `code` an integer number for automated processing of the logs (usually has different meaning for different applications, see `app` field);
* `capture_time` the timestamp of when the log entry was created;
* `description` a human-readable log message.

*Optional fields:*

* `app` a name of application that the log message is generated by (e.g. "cvmain", "cvmqtt", "cvupgrader" or any client-specific app name);
* `version` a version of log message for given `app` (normally codes shouldn't change but if they do then `version` should indicate those backwards incompatible changes);
* `priority` an indication of how important this message is (valid values are: "vvv_low", "vv_low", "v_low", "low", "norm", "med", "high", "v_high", "vv_high", "vvv_high", "extreme");
* `level` a logging level which indicates importance of log entry (severity of an issue if there's one);
* `parameters` a JSON array or object of any structure for automatic processing (normally the structure must be fixed for each `app`+`version`+`code` combination).

#### Response

*Success:*

All the submitted log entries are processed (invalid entries are ignored) and should not be submitted again.

* Response code: `200 OK`
* Response body: `none`

*Validation failure:*

Request body is missing or invalid.

* Response code: `400 Bad Request`
* Response body: `application/json`

```json
{
  "errors": [
    {
      "message": "Missing or invalid request body"
    }
  ]
}
```

## POST `/audit/diagnostics/log`

Submit unit audit log(s) for diagnostics. Open a new diagnostic report (see `GET /audit/diagnostics/reports` for more details) for the calling unit or attach the log(s) to the most recent `open` one.

As long as there is an `open` diagnostic report for the unit the submitted logs will overwrite what's attached to the report. If there's no `open` report a new one will be created.

#### Access: `unit`, no permissions required

#### Request body: `application/json`

See `POST /audit/log`.

#### Response

See `POST /audit/log`.

## POST `/audit/diagnostics/archive`

Generate an archive upload URL for the most recent `open` diagnostic report for the calling unit. A new report will be automatically opened if it does not exist.

As long as there is an `open` diagnostic report for the unit the submitted archive will overwrite the one attached to the report. If there's no `open` report a new one will be created.

The upload URL will expire after some time (configurable) so if a unit fails to upload the archive before URL expiration then it will have to generate another URL and try again.

#### Request body: `application/json`

```json
{
  "filename": "test.tar.gz",
  "checksum": "sN44SCDG/21z0DPip1wbpw==",
  "content_type": "application/gzip"
}
```

*Required fields:*

* `filename` a filename as it will be stored and downloaded afterward;
* `checksum` a base64-encoded MD5 checksum of the file contents;
* `content_type` a MIME type of the file to be uploaded (e.g. `application/gzip`).

#### Response

*Success:*

* Response code: `200 OK`
* Response body: `application/json`

```json
{
  "url": "https://..."
}
```

To upload the file perform `PUT` request to given URL and submit the file as request body.
Make sure to specify `Content-Type` and `Content-MD5` headers. Their values must match to what have been submitted to `/audit/diagnostics/archive` endpoint before.

## POST `/management/user`

Create new user/supervisor.

An e-mail with invitation link/code will be sent to the user.

When creating a new user you must specify its initial permissions (see [security] document). To adjust permissions
afterward (see `PUT /management/user/{id}/permissions` endpoint) you will need `user.permissions.edit` permission with
proper targets.

#### Access: `user` or `supervisor` having `user.create` permission

To create user within certain account you need that account to be a permission target of `user.create` permission.
To create supervisor you need `urn:*` as a permission target of `user.create` permission.

#### Request body: `application/json`

```json
{
  "account_id": "0697b16e-ddcc-4711-b072-906fdcc05270",
  "username": "John.Doe@VaultGroup.Co.Za",
  "full_name": "John Doe",
  "permissions": [
    {
      "tokens": [
        "unit.view",
        "unit.edit"
      ],
      "target_urns": [
        "urn:*"
      ]
    }
  ]
}
```

*Required fields:*

* `username` a unique name of the new user (will be converted to lower case during saving);
* `permissions` the permissions to be granted to the new user. You cannot give new user an access wider than you have so
  all the specified permissions and permission targets will be validated and automatically erased to meet that
  requirement.

*Optional fields:*

* `account_id` an identifier of an account to create user within (omit to create a supervisor);
* `full_name` a full name of a user, can be used as a description (up to 255 characters).

#### Response

*Success:*

* Response code: `200 OK`
* Response body: `application/json`

```json
{
  "id": "32af44d2-ae7d-44e8-9eb4-38580c3da77c",
  "account": {
    "id": "0697b16e-ddcc-4711-b072-906fdcc05270",
    "name": "Test account"
  },
  "username": "john.doe@vaultgroup.co.za",
  "full_name": "John Doe",
  "active": false,
  "invitation": {
    "code": "98gTlqbHCi9H9gXhaIOhVdGJnb4OTKJQnZCHNrAD1ZfOm89Iguev9YUbMrRkqZ43",
    "creation_date": "2022-05-09T09:14:38.760430915Z",
    "expiration_date": "2022-05-10T09:14:38.760430915Z"
  },
  "creation_date": "2022-05-09T09:14:38.760430915Z",
  "change_date": "2022-05-09T09:14:38.760430915Z"
}
```

Notice that `invitation.code` property is only available on user creation. It will not be available for reading
afterwards.

## POST `/management/vpn/enable`

Allocate a VPN channel for current user (if not exist yet) or generate new password (optional) for existing channel.

There are two types of VPN clients: users (supervisors) and units.

For each type there is a separate pool of channels with dedicated IP-addresses.
Typically, users' addresses are 10.8.1.N and units' addresses are 10.8.2.N but make sure to consult with deployment configuration.
Username for a user is always `userN` (where `N` is the number of the channel which is also the last octet of the IP-address)
while username for a unit is always `unitN` (having that `N` as the last octet of its IP-address too).

Once you enable VPN for yourself for the first time a new channel is allocated. You get a channel number and a password in response
which means you know your username (`"user" + the channel number`) and can connect to the VPN server. You can keep those
credentials for as long as you like.

If you try to enable VPN again (while it's enabled) you will get the same channel number but no password this time.
The plain text password is not stored in a database so you can't recover it if you lose it, but you can generate a new one.

To generate a new password for your existing channel you set `always_update_password` to `true` calling this endpoint.

Warning: the total number of channels is limited so the system may reassign existing channels (taking them from their owners)
starting with the oldest one.

In a very unlikely situation when the number of supervisors actively trying to access VPN exceeds the channel pool size
and every channel has been activated (or re-activated) less than X minutes ago a reassignment will not be allowed.
Then you would get `429 Too Many Requests` response.

#### Access: `supervisor` having `unit.vpn` permission

#### Request body: `application/json`

```json
{
  "always_update_password": true
}
```

*Optional fields:*

* `always_update_password` whether or not a new password must be generated even if a channel already exists.

#### Response

*Success (new channel allocated):*

* Response code: `200 OK`
* Response body: `application/json`

```json
{
  "user_channel": 1,
  "user_password": "RdAvy3h5dyAnJZYjl8CSqVnd9pRtTn1o"
}
```

*Success (channel already exists):*

* Response code: `200 OK`
* Response body: `application/json`

```json
{
  "user_channel": 1
}
```

*Cannot allocate or reassign:*

* Response code: `429 Too Many Requests`
* Response body: `application/json`

```json
{
  "errors": [
    {
      "message": "All user channels are in use. Try again later."
    }
  ]
}
```
